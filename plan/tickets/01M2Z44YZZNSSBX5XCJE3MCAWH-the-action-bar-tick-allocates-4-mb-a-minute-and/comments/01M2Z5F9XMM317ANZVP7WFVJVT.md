Not settled, and it needs a session. Countdown does not obviously account for 4 to 5 MB a minute on its own: ten strings a second per sweeping square against the roughly 1650 a second that figure implies. Two things could close that gap and neither can be read off the source. Lua 5.1 interns strings, so the cost depends on how many of the readings are alive at the moment of the format, and a countdown crossing tenths never repeats a reading inside its own sweep. And a `collectgarbage("count")` delta over a 0.1 s bracket is a coarse instrument. Read `oursAlloc` and `allocKey` again on the next session past minute 35: if `action` is still the key, the rest is not in this file and the next place to look is what the secure button attribute reads cost, which no Lua-side counter can see.

Fix. `UI/Ability.lua`. Quantum is unchanged; it already offsets its three scales out of each other and already decides which reading a number is worth. Countdown now takes that integer instead of the seconds and is a lookup into `LABEL`, a table built once at load: 100 tenths, the 50 whole seconds from 59 to 10, and 180 minutes. `Ability.Draw` passes `tick` rather than `remaining`, so the thing that picks the scale and the thing that writes it cannot disagree. A tick with no string is the blank, which is a cooldown past three hours or a remaining that went negative between the client clearing it and the next tick; the old code drew "-0.0" there. `Buttons/Bars.lua` and `Buttons/Slot.lua` needed no change.

The harness is where this was invisible and that is fixed too. 04-ability-square asserted 0.00 KB over 50 *unchanged* redraws, and an unchanged redraw never enters Countdown at all: Ability.Draw only calls it on the tick Quantum says the reading moved. There is now a second figure over a square whose number is moving, 330 readings down through all three scales, asserted flat and asserted to have written all 330. It reads 8.91 KB against the countdown as it was and 0.00 KB against the fix.

One trap in that test, worth knowing before writing another like it. The recording pass has to come *after* the weighed pass. Lua 5.1 interns strings, so holding all 330 readings alive in a set and then rebuilding them hands each one straight back from the string table and the weighed pass reads 0.00 KB against the unfixed code. That is also the answer to why this is garbage in the game and not in a test: SetText copies into the client, nothing in Lua holds the string, and the next tenth of a second builds it from nothing.
